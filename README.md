# Микросервисы: принципы

## 1. API Gateway  
Некоторые возможности программных решений, обеспечивающих реализации API Gateway  

| Решение | Агрегация данных | Мониторинг и логирование | Балансировка нагрузки | Кэширование ответов |
| ------------- | ------------- | ------------- | ------------- | ------------- |
| NGINX | нет | Поддерживается через модули | Поддерживается через конфигурацию | нет |
| Kong | да | Встроенные инструменты мониторинга | Гибкая масштабируемость с балансировкой | да | да |
| Amazon | да | Встроенный мониторинг | Автоматическая масштабируемость | нет | нет |
| Apigee  | да | Мониторинг через Apigee Analytics | Высокая масштабируемость с ограничением скорости запросов | нет | нет |
| Azure   | с помощью Azure Functions | Монитoринги чeрез Azure Monitor | нет | нет |
| Yandex  | пpи интегpaции c Yandex Cloud Functions | Доступнo в Yandex Monitoring | Не поддерживается явно | Не поддерживается напрямую |

все эти решения соответствуют требованиям:   
1. обеспечение маршрутизации запросов к сервису  
2. возможность проверки аутентификационной информации в запросах  
3. обеспечение терминации HTTPS  
  
На основе перечисленных решений предпочтение отдается Kong  

Осноные причины выбора  
1. Гибкость и масштабируемость: предлагает гибкую систему плагинов, которая позволяет легко расширять функциональность шлюза без изменения основного кода  
2. Маршрутизация запросов и аутентификация: поддерживает маршрутизацию запросов на основе конфигурации и обеспечивает проверку аутентификации через различные плагины (OAuth, JWT)  
3. Терминация HTTPS: поддерживает терминацию HTTPS для шифрования данных между клиентом и шлюзом  
4. Мониторинг и логирование:  встроенные инструменты мониторинга позволяют отслеживать производительность системы и выявлять ошибки в режиме реального времени  
5. Балансировка нагрузки:  Гибкая масштабируемость с балансировкой позволяет эффективно управлять трафиком приложения  
  
Основные преимущества перед другими системами  
1. Больше гибкости в настройке за счет открытого исходного кода  
2. Низкая стоимость эксплуатации без необходимости сложных лицензионных соглашений  
3. Не зависит от конкретной облачной платформы  
4. Широкий спектр возможностей по расширению через плагины против более ограниченного набора стандартных  


## 2. Брокер сообщений

На основе сравнения возможностей брокеров сообщений, я бы выбрал Apache Kafka  

Основные причины выбора  
1. Высокая производительность и масштабируемость: способен обрабатывать миллионы сообщений в секунду, что делает его идеальным для высоконагруженных систем  
2. Отказоустойчивость и репликация данных: обеспечивает надежное хранение и дублирование данных между узлами кластера, что позволяет восстановиться после сбоя системы  
3. Поддержка потоковой обработки: Подходит для приложений, требующих обработки больших объемов данных в реальном времени  
4. Гибкая модель потребления сообщений: Использует темы и разделы для постановки сообщений в очередь, позволяя потребителям получать данные из раздела независимо от порядка их отправки  
5. Простота интеграции с другими сервисами: Может быть легко интегрирован с различными инструментами через API или сторонние библиотеки (например,Confluent)  
  
Преимущества перед другими решениями  
1. высокая пропускная способность за счет последовательного дискового ввода-вывода  
2. не зависит от конкретной облачной платформы  
3. предлагает надежную систему хранения на диске  
4. широкие возможности по настройке топиков и разделов для гибкой маршрутизации сообщений  

Недостатки  
Основным недостатком может быть сложность первоначальной настройки кластера Kafka без опыта работы с распределенными системами
